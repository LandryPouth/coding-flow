# Design decisions and rejected options

> What was decided, what was refused, and — the part that is usually lost — **why
> the refusals were refused**. A rejected option with no recorded reason comes back
> every six months and gets re-argued from scratch.
>
> This is hand-written and durable. It is not `docs/DECISIONS.md`, which is
> generated by `ai-flow audit --decisions` from the `## Decisions` sections of
> individual stories.

## How to read this file

Each entry names the proposal, the verdict, and the reason. Reasons that are
**measurements** are marked as such and carry their numbers, because a measurement
can be re-run and disproved, while an opinion can only be re-argued.

Where a decision is enforced by something — a test, a document, a config key — the
enforcement is named. An entry with no enforcement is only a memory.

## 1. Risk is read from the diff. Prose caps at `medium`

**Decided 2026-08-18. Shipped in 0.8.0.** Enforced by `test/harness.test.js`
(three cases) and `test/coverage-gate.test.js`.

`scoreStoryRisk` substring-matched 17 terms across the whole story text, and one
hit meant `high`. Because `combineRisk` takes the max of the story and diff scores,
the prose side was pinned at `high` and `scoreDiffRisk` — the path-based one — could
never win a single time.

**Measurement.** 13 days of real use on `imob`, a project this tool did not design:
**39 of 39 evidence records scored `high` / `recommendedMode: strict`.** `auth` fired
inside "author", `token` inside "design tokens", `migration` inside a story titled
*color migration*. Every change paid TDD, Security Questions and a mandatory deep
review — including a hero-section recomposition.

**The finding that generalises**, and the reason the first fix was wrong: adding
word boundaries moved the number from 92% to 90%. One story. The terms are *genuinely
in the text*, because a spec names what it is near — "does not touch auth", a file
list, an acceptance criterion — as readily as what it changes. **Scoring risk from
prose is structurally unsound, not merely badly tuned.** Any future risk signal must
come from the diff.

Replayed over the same 39 records after the fix: **100% STRICT → 31%**, and the 12
survivors are real (`schema.prisma`, `migration.sql`, `auth.controller.ts`).

Prose still lifts a quiet change to `medium`, so the coverage gate fires exactly
where it fired before. The ceremony was the bug; the proof was not.

## 2. The guard stays one process per decision — no resident daemon

**Refused 2026-08-18.** Recorded in `docs/agent-contract.md` under *the core stays
boring*.

The proposal: keep a long-lived Node process and turn the hook into an IPC ping,
taking the guard from ~125 ms to ~3 ms — the technique behind `git cat-file --batch`
and `tsserver`.

**Refused on correctness, not on effort.** The guard is fail-open by design with a
60 s timeout. A daemon that is dead, hung, or serving a cached `harness.json` stops
protecting **silently** — which is strictly worse than the latency it buys. Add
worktree-scoped socket lifecycles, orphan reaping, and a locally reachable
"may I write this?" endpoint, and the security surface grows to save time that is
spent between two multi-second LLM turns anyway.

**Measurement that made it moot.** The guard was never the cost. Median verify on
`imob`: 24.9 s, one per story. Total machine time across 43 stories and 13 days:
51 minutes. Against a ~1h30 story, the guard's 50 invocations were **~0.1%**.

What *was* taken instead, because it changes nothing about the execution model:
dispatching `guard` before the other 20 modules load, and keeping `crypto`
(OpenSSL bindings) off its path. Overhead above bare Node startup: **67.8 ms →
26.2 ms**, measured with interleaved sampling. Pinned by a module-graph assertion in
`test/guard.test.js`.

> Method note, worth keeping: on WSL2 two consecutive runs of the *same* command
> gave 67 ms and 132 ms medians. The noise was larger than the effect. Every number
> above comes from interleaved sampling (alternating cases within one loop) to
> cancel machine drift. A single-shot timing on this class of machine is not
> evidence.

## 3. No rewrite in Go. No rewrite in Python

**Refused 2026-08-18.**

Go would genuinely fix process startup (~4 ms vs ~57 ms). It is still refused: it
kills `npx @landry_pouth/coding-flow`, the fallback the skills themselves document
for machines where the binary is not on `PATH`; it kills the zero-dependency
`node:test` suite; and it buys back ~0.1% of a story. Python was never a candidate —
~46 ms of startup, the same order as Node.

A **Go binary for the guard alone** is the more honest version of the idea and is
also refused: two implementations of one security policy will diverge, and a
divergent security policy costs more than 80 ms. It only becomes viable if the Node
guard is deleted, which means per-platform `optionalDependencies` and a release
pipeline. Reconsider if real users ever complain about latency — as of 0.8.0, none
have; the complaint was about *ceremony*, and that was entry 1.

## 4. Policy never moves into `SKILL.md` frontmatter

**Refused 2026-08-18.** Recorded in `docs/agent-contract.md`.

The proposal: declare a skill's expectations in its frontmatter (`evidence:`,
`exit_conditions:`, `min_patch_coverage:`) and have the CLI read them, so the CLI
"understands" the workflow it is enforcing.

It inverts the contract. A `SKILL.md` is agent-facing text that the agent can edit,
so an agent that lowers its own threshold has defeated the gate while staying inside
the rules. Thresholds live in `.coding-flow/harness.json` — project configuration,
not prompt. The one-line boundary: **skills are behaviour, `harness.json` is
policy.** Behaviour is advisory and may be reworded freely; policy is enforced and
changes deliberately.

## 5. What was taken from `addyosmani/agent-skills`, and what was not

Reviewed 2026-08-18 (88k stars, 24 skills, MIT). The most useful thing about it is
what it proves: **a skills layer is a commodity.** Their `## Verification` section
is a checklist an agent ticks for itself; ours is `ai-flow verify` returning
`NOT PROVEN`. That difference is the product.

**Taken** — all of it prose-level, all of it net-neutral or negative in line count:

- `## Common Rationalizations` tables in `flow-run` and `flow-review`. Their real
  invention: pre-writing the rebuttal to the excuse, so an agent reaching for one
  meets an answer instead of reasoning. Ours were *extracted* from prose already in
  the skills, not added.
- `## Red Flags` in `flow-run` — signals you have already drifted, distinct from
  Stop Conditions, which are where you stop and hand back.
- A **500-line ceiling** per `SKILL.md` with progressive disclosure, one level deep.
  Enforced by `test/ceremony.test.js`.

**Not taken**:

- **24 skills, 8 phases, a 16-step lifecycle.** That is the "second BMAD" failure the
  freeze exists to prevent. Seven flat skills is a choice.
- **Specialist agent personas.** Runtime orchestration, which this tool refuses.
- **Their `definition-of-done.md`.** Seductive, but it is an honour-system checklist —
  the degraded form of `ai-flow verify`. Importing it would dilute the argument.
- **Behavioural evals with an LLM in the loop.** Non-deterministic, dependency-heavy,
  and they sample what `verify` already guarantees mechanically. The useful residue
  was a deterministic test: `skills/` and `templates/.claude/skills/` are two shipped
  copies that must stay byte-identical, and nothing compared them until 0.8.0.
- **Their multi-agent packaging.** They ship no enforcement layer, so there is nothing
  to port for the only hard part. See `docs/plans/multi-agent-install.md`.

## 6. `ai-flow report` — the one admitted freeze exception

**Dropped, then shipped, on 2026-08-18.**

`report` was rejected that morning for failing the standing test — *"if I don't
implement it, does the tool fail at its mission?"* It was a differentiation argument
(competitors execute nothing, so they structurally cannot produce it), not a
reliability one, and there were no users to differentiate for.

Both halves of that premise fell within the day: the tool was about to be handed to
people who are not its author, and the only other feedback channel was "they describe
what broke" — assertion in place of evidence, which is the exact failure the tool
exists to reject.

**The precedent is deliberately narrow: a freeze exception requires the premise of
the original rejection to have changed, stated out loud. Not a better argument for
the same feature.** Two exceptions in one day is the point at which a freeze stops
existing; the second candidate (multi-agent) was refused on exactly this basis and
deferred until the new channel produces evidence that anyone wants it.

## 7. Diagnose from `.coding-flow/runs/` before theorising

**Method, not a decision.** The most expensive mistake of the 0.8.0 cycle was almost
made three times: two separate analyses concluded the tool was slow and proposed
architectural surgery (a daemon, a language rewrite), and a third — this one —
proposed word boundaries. **All three were wrong, and the recorded evidence said so
in about ten minutes.**

The tool records `durationMs` per command, risk level, recommended mode, coverage
rung, and exit codes on every run. Read them first. `ai-flow report` renders exactly
this, which is the other reason it earned its exception.

The corollary that stung: `coding-flow` itself had `.coding-flow/` present with
`validation.commands: []` and **zero runs** — an install that looked like dogfooding
and proved nothing. Fixed in 0.8.0, and the first real `verify` immediately caught a
regression that per-file test runs had missed.

## 8. A test file that only got weaker does not count as "a test changed"

**Decided 2026-08-18. In progress.**

The coverage gate's weaker rung, `evidence`, is earned when a behaviour file and a
test file both appear in the diff. **The direction of the test change is never
read.** So the cheapest way past the gate is to touch a test — and deleting
assertions, adding `.skip`, or removing a test file outright all touch a test.

That is a hole in the proof, not a missing feature: `evidence` already claims less
than `verified`, but it is currently satisfiable by a diff that made the suite
*worse*. An agent does not need to be adversarial to land there — "the test was
failing, so I removed the assertion" is an ordinary, well-meaning move.

**The fix is narrow on purpose.** It is not a new gate:

- A test file whose diff is **only** weakening does not count toward `evidence`.
  A diff whose test changes are all weakening lands exactly where a diff with no
  test change lands — `NOT PROVEN`, with the existing `## Test Exemption` escape.
- Weakening is **always reported**, at every rung, including `verified`. Measuring
  92% patch coverage while three tests were deleted is a fact the human must see;
  suppressing it because the number was green would be the same dishonesty the
  coverage rungs exist to prevent.
- **No new blocking configuration.** It rides on `requireTestChange`. Adding a
  second switch would mean a second thing to turn off.

**Detection, and its honest limits.** Three signals over the diff of files matching
`testGlobs`, in descending confidence: a test file **deleted**; **skip/only markers
added** (`.skip(`, `.only(`, `xit(`, `@pytest.mark.skip`, `t.Skip(`, `#[ignore]`, …);
and **net assertion count decreased**. The third is a heuristic over regexes, not a
parse — it cannot tell a weakened test from a legitimately refactored one.

That limit is why it reports rather than blocks on its own, and why `.only(` is
treated as weakening: it does not skip the test it marks, it silently skips every
*other* test in the file, which is worse and trivially detectable.

**Prior art:** Shipmoor (`shipmoor.dev`) advertises detection of "deleted or gutted
tests" as part of its verdict. Same hole, independently found — which is the useful
signal here, not the feature.

## 9. Binding acceptance criteria to evidence — designed, not built

**Written 2026-08-18. Not started, and not scheduled.**

Today a story's acceptance criteria are prose, and the thing that decides whether
they are met is the agent that wrote the code. `verify` proves the *commands* ran
and passed; nothing connects criterion 3 to the test that would fail if criterion 3
regressed. The gap is real: a story can be `verified` with every criterion
unimplemented, provided the suite is green.

The shape that would close it — freeze each criterion into an obligation, bind each
obligation to a named piece of evidence, and emit a verdict per obligation rather
than per story — is what Shipmoor calls Claim Check (`READY` / `READY WITH GAPS` /
`BLOCKED` / `INCONCLUSIVE`).

**It is not being built, for two reasons.**

First, the binding has to come from somewhere, and every available source is the
agent: the agent writes the criteria, names the tests, and would declare the
mapping. A binding an agent authors is a binding an agent controls — the same
objection that killed policy in `SKILL.md` frontmatter (entry 4). A version that is
actually enforced needs a source of truth the agent does not write, and there isn't
one yet. Without that, this is `evidence`-grade proof wearing a `verified` label,
which is the exact failure the coverage rungs were built to prevent.

Second, it is a new subsystem, not a config key — squarely what the freeze exists to
refuse, and "a competitor ships it" is not a change of premise (see entry 6).

**The honest smaller step, if this is ever picked up:** report which acceptance
criteria have *no* named validation at all. That is derivable from the story files
alone, it blocks nothing, and it would tell a human where to look. Start there, and
only there, and see whether anyone uses it before building the verdict machinery.
