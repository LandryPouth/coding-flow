# How AI-coding planning tools and methods turn an idea into implementation-ready work (2025-2026)

Research date: 2026-11-13. Every claim is dated by its source; "fetched 2026-11-13" means read from the live repo/docs that day (main branch). Scope addition from the user: Coding Flow is mainly for backends and non-web projects (Python, Go, Rust, Java/Kotlin, C#, C/C++; games, networking, CLIs, embedded, data/ML, mobile, libraries), so each tool is tagged for web/JS bias vs language/domain agnosticism.

## Q1. Per-tool workflow: inputs, steps, artifacts, context gathering, uncertainty handling, handoff

### Takeaway
By late 2026 the leading tools converged on the same skeleton (durable project memory, then intent, then clarification, then design, then tasks, then a consistency/readiness check, then execution), but the newest versions (spec-kit 1.x, BMAD v6.12/v7, Matt Pocock skills, superpowers) all moved *away* from one mandatory pipeline toward "right-sized" entry points, and they split "figuring out what you want" (brainstorm/grill/research/idea assessment) from "writing the contract" (spec). Most are language-agnostic in mechanism; the web bias shows up in examples, UX artifacts and the "schema/API/UI" definition of a vertical slice.

### Cited Findings

**GitHub spec-kit** (latest release v1.4.0, 2026-11-10, per GitHub releases API)
- Core commands in README (fetched 2026-11-13): `/speckit-constitution`, `/speckit-specify`, `/speckit-plan`, `/speckit-tasks`, `/speckit-implement`, `/speckit-converge`; `clarify`, `checklist`, `analyze` remain as command templates. — [spec-kit README](https://github.com/github/spec-kit)
- 2026 restructuring: README now offers independent entry points "not mandatory phases": SDD (core), Bug fixing (extension: `bug-assess`, `bug-fix`, `bug-test`), and **Idea assessment** (extension: `assess-intake`, `assess-research`, `assess-define`, `assess-shape`, `assess-decide`) ending in `decision.md` with `go` / `needs-clarification` / `kill`; "Stopping with a documented reason is also a useful outcome"; the `decision.md` handoff summary is passed to `/speckit-specify`. Extensions, presets (e.g. "requiring regulatory traceability in plans"), workflows and bundles customize the process. — [spec-kit README](https://github.com/github/spec-kit)
- Philosophy doc: `/specify` turns a description into a numbered feature branch + `spec.md`; `/plan` checks constitutional compliance and produces `plan.md`, `research.md`, `data-model.md`, `contracts/`, `quickstart.md`; `/tasks` writes `tasks.md` with `[P]` markers for parallelizable tasks. Templates force `[NEEDS CLARIFICATION: specific question]` markers instead of guessing; spec is not complete while any remain. — [spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md)
- Constitution articles (default example): I Library-First, II CLI Interface (text I/O, JSON), III Test-First "NON-NEGOTIABLE" (tests written, approved, confirmed to fail), VII Simplicity ("Maximum 3 projects for initial implementation", no future-proofing), VIII Anti-Abstraction ("Use framework features directly"), IX Integration-First (contracts, contract tests, real DBs over mocks). Exceptions go in a "Complexity Tracking" section. — [spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md)
- `/plan` command: fill Technical Context marking unknowns "NEEDS CLARIFICATION"; evaluate gates ("ERROR if violations unjustified"); **Phase 0** generates `research.md` by turning each NEEDS CLARIFICATION into a research task and dispatching research agents ("Research {unknown} for {feature context}"), output "research.md with all NEEDS CLARIFICATION resolved"; **Phase 1** data-model, contracts, quickstart; command "ERROR on gate failures or unresolved clarifications". — [templates/commands/plan.md](https://github.com/github/spec-kit/blob/main/templates/commands/plan.md) (fetched 2026-11-13)
- Handoff: tasks.md → `/speckit-implement`; `/speckit-converge` closes the loop (README, fetched 2026-11-13). — [spec-kit README](https://github.com/github/spec-kit)

**Kiro (AWS) spec mode**
- Each spec = `requirements.md` (or `bugfix.md`), `design.md` (architecture, sequence diagrams, error handling, testing strategy), `tasks.md`. Feature specs have Requirements-First and Design-First variants. Bugfix specs record current, expected and **unchanged** behavior (regression guard). Each phase reviewed via a Markdown Review UI with comments. "Run all tasks" builds a dependency graph and runs independent tasks in concurrent **waves**. **Quick Spec** generates all three artifacts in one pass without approval gates. Page last updated 2026-11-12. — [kiro.dev/docs/specs](https://kiro.dev/docs/specs/)
- Requirements use "As a…" stories with GIVEN/WHEN/THEN-style criteria; tasks trace back to requirement numbers; steering (memory bank) defaults to `product.md`, `structure.md`, `tech.md` (Böckeler, 2025-10-15). — [Martin Fowler site](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- Steering lives in `.kiro/steering/`; product.md = purpose, target users, key features, business objectives; requirements in EARS notation ("Easy Approach to Requirements Syntax", event/condition-driven "the system shall" statements). Mostly third-party descriptions; official steering page exists. — [Kiro CLI steering docs](https://alpha.us-east-2.kiro.adc.aws.dev/docs/cli/steering/); [codemyspec on Kiro EARS](https://codemyspec.com/blog/kiro-specs-explained)

**BMAD Method** (stable v6.12, latest tag v6.12.4 2026-10-14; v7 in preview alpha, "ETA mid-November 2026")
- Repositioned as "Agile AI Driven Development": "the process sizes itself to the work"; entry skill `bmad-build`, guide skill `bmad-help`. Delivery loop: vague notion → Clarify; big clear idea → Plan; small change → Build and verify; Learn and adjust loops back. — [BMAD README](https://github.com/bmad-code-org/BMAD-METHOD)
- Planning path rule: "is the intent already well defined?" If yes → `bmad-spec`; if not, use independent tools "not stages". "A well-defined intent says what should be true when the work is done, what must not change, and what is out of scope". `bmad-spec` input ceiling "a few tens of thousands of tokens, roughly a 40-page document"; raw piles "silently los[e] the parts that mattered; condense them first". "The spec skill writes the contract; it does not help you figure out what you want." — [Choose a Planning Path (V6.12)](https://github.com/bmad-code-org/BMAD-METHOD/blob/V6.12/docs/plan/choose-a-planning-path.md)
- Skill → artifact map (V6.12): `bmad-brainstorming` (brainstorm.html + brainstorm-intent.md); `bmad-forge-idea` ("pressure-test an idea until it hardens, proves out, or dies cheaply"; forge-report.html, forged-idea.md); `bmad-deep-recon` (cited `research.md`); `bmad-product-brief` (brief.md + addendum.md); `bmad-prfaq` (working backwards from press release); `bmad-prd` (prd.md, addendum.md, `.memlog.md`; also a *validate* mode); `bmad-ux` (DESIGN.md, EXPERIENCE.md); `bmad-spec` (SPEC.md + optional stories.yaml); `bmad-architecture` (`ARCHITECTURE-SPINE.md`: "technical decisions that keep separately built parts consistent"); `bmad-create-epics-and-stories`; `bmad-sprint-planning` ("Check readiness before implementation", PASS/CONCERNS/FAIL + sprint-status.yaml). Also `bmad-generate-project-context` / `bmad-project-context` for brownfield, and ship skills `bmad-correct-course`, `bmad-retrospective`. — same source + [repo tree V6.12](https://github.com/bmad-code-org/BMAD-METHOD/tree/V6.12/src/bmm-skills)
- Persona agents still exist: analyst, PM, architect, UX designer, dev (`src/bmm-skills/agents/`). — [repo tree](https://github.com/bmad-code-org/BMAD-METHOD/tree/V6.12/src/bmm-skills/agents)

**Matt Pocock skills** (repo last commit 2026-11-12)
- 2026 set: `grilling` (primitive), `grill-me`, `grill-with-docs` (builds `GLOSSARY.md` + ADRs inline, DDD "ubiquitous language"), `domain-modeling`, `to-spec` ("No interview, just synthesizes what you've already discussed"; publishes to issue tracker; "quizzes you about which modules you're touching"), `to-tickets` (formerly prd-to-issues), `wayfinder` (multi-session planning), `to-questionnaire`, `tdd`, `triage`, `improve-codebase-architecture`. — [mattpocock/skills README](https://github.com/mattpocock/skills)
- `grilling` now works a **design tree** in **rounds**: the "frontier" = decisions whose prerequisites are settled; ask the whole frontier at once, numbered, each with a recommended answer, worded "so 'yes' accepts your recommended answer". "Finding facts is your job, never the user's" — dispatch a sub-agent for environment facts, don't block other questions on it. Done "when the frontier is empty… nothing left silently assumed", and not acted on until the user confirms shared understanding. — [grilling SKILL.md](https://github.com/mattpocock/skills/blob/main/skills/productivity/grilling/SKILL.md) (fetched 2026-11-13). Note: this replaces the earlier (2025) "one question at a time" grill-me style.
- `to-tickets`: tracer-bullet vertical slices, each "a narrow but COMPLETE path through every layer (schema, API, UI, tests)", "demoable or verifiable on its own", "sized to fit in a single fresh context window", prefactoring first ("Make the change easy, then make the easy change"), explicit **blocking edges**; wide refactors are the exception, sequenced **expand–contract** (expand, migrate in batches sized by blast radius, contract). Then quiz the user on the breakdown. — [to-tickets SKILL.md](https://github.com/mattpocock/skills/blob/main/skills/engineering/to-tickets/SKILL.md)
- `wayfinder`: for work "too big for one agent session"; a map issue with **Destination**, Notes, "Decisions so far" index; child **decision tickets** resolved one at a time; "Plan, don't do… produce decisions, not deliverables"; "The map is domain-agnostic". — [wayfinder SKILL.md](https://github.com/mattpocock/skills/blob/main/skills/engineering/wayfinder/SKILL.md)

**obra/superpowers** (fetched 2026-11-13)
- `brainstorming`: mandatory before creative work "in software or out of it". Triage: if everything is in the request, just do it; else converse. Order: lay out approaches and have the human pick, write design doc (short or full), get approval, then invoke writing-plans. "Look Before You Ask": read the referenced code until you can explain how it works today; "Never ask what the project or their context already answers." First message ~200 words: echo request (what/who/why), add findings, flag constraints/conflicts/cheaper paths; if the *why* is missing, ask one open question; otherwise ask the single question "that would change it most", with concrete options and a recommendation. — [brainstorming SKILL.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md)
- `writing-plans`: plan for "an engineer who has not seen this codebase"; document what they cannot know: "which files, which names and signatures, which values from the spec, which tests prove each task". Scope check (split independent subsystems into separate plans); File Structure mapped before tasks ("Split by responsibility, not by technical layer"); task = "smallest unit that carries its own test cycle and is worth a fresh reviewer's gate"; steps are single checkable actions (write failing test, run it, implement, run, commit). Header with Goal, Architecture, Tech Stack, Spec path, Global Constraints. Saved to `docs/superpowers/plans/YYYY-MM-DD-<feature>.md`; handoff to subagent-driven-development or executing-plans. — [writing-plans SKILL.md](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md)

**OpenAI Codex ExecPlans (PLANS.md)** (cookbook recipe, now marked archived)
- Mandatory living sections: Progress (only place for checklists), Surprises & Discoveries, Decision Log, Outcomes & Retrospective; plus Purpose/Big Picture, Context and Orientation, Plan of Work, Concrete Steps, Validation and Acceptance, Idempotence and Recovery, Interfaces and Dependencies. "Fully self-contained", "Treat the reader as a complete beginner to this repository", prose over lists, "Milestones are narrative, not bureaucracy", explicit prototyping milestones with promote/discard criteria, "Every ExecPlan must produce a demonstrably working behavior", "do not prompt the user for 'next steps'". Claim: a similar plan "enabled Codex to work for more than seven hours from a single prompt". — [OpenAI cookbook: Using PLANS.md](https://developers.openai.com/cookbook/articles/codex_exec_plans)

**Task Master AI** (latest release task-master-ai@0.43.1, 2026-03-31)
- Three model roles: main, **research**, fallback; research via Perplexity, xAI, OpenRouter etc.; "Using the research model is optional but highly recommended." — [claude-task-master README](https://github.com/eyaltoledano/claude-task-master)

### Inferences
- The common "readiness gate" pattern is now explicit in three tools: spec-kit `/plan` ERRORs on unresolved clarifications, BMAD `bmad-sprint-planning` returns PASS/CONCERNS/FAIL, Matt Pocock's grilling ends only when the frontier is empty. Coding Flow's existing readiness gate is aligned with the field.
- The biggest structural gap versus /flow-plan is the **pre-spec stage**: spec-kit idea assessment (go/clarify/kill), BMAD forge-idea/deep-recon/product-brief/PRFAQ, superpowers' "why" question. All treat "do we understand the product?" as a separate step that may end in "stop".
- Two handoff styles: rich per-task instructions for a novice executor (ExecPlans, superpowers) vs thin tickets with blocking edges executed in fresh contexts (to-tickets, Kiro waves, spec-kit `[P]`).

## Q2. Which tools integrate web research / external docs during planning, and how

### Takeaway
Research is now a first-class, *typed*, *cited* planning artifact in spec-kit (`research.md`, plus an `assess-research` stage) and especially BMAD (`bmad-deep-recon` with market/domain/technical/competitive/user-voice/academic types, three modes). Task Master delegates to a separate "research model" (Perplexity etc.). Superpowers, Matt Pocock, ExecPlans and Agent OS rely on codebase reading, not web research.

### Cited Findings
- spec-kit `/plan` Phase 0: every unknown in Technical Context becomes a research task dispatched to research agents; results consolidated in `research.md`; Phase 1 cannot start until it is complete. — [plan.md template](https://github.com/github/spec-kit/blob/main/templates/commands/plan.md)
- spec-kit philosophy: research agents investigate "library compatibility, performance benchmarks, and security implications" and organizational constraints; the doc does not say how sources are gathered. — [spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md)
- spec-kit Idea assessment extension has a dedicated `/speckit-assess-research` step before define/shape/decide. — [spec-kit README](https://github.com/github/spec-kit)
- BMAD `bmad-deep-recon`: "when a planning decision should rest on evidence rather than assumption"; "not only for software"; output "a cited research.md that a PRD or product brief can read without reprocessing". Types = "a set of questions, source rules, and freshness windows": market, domain, technical, competitive, user-voice, academic-lit; Explore vs Select (structured choose-between). Modes: **Draft** (writes a prompt for the user's own deep-research tool: ChatGPT, Gemini, Grok, Perplexity), **Process** (files an external report, checks claims against the type), **Run** (search, verification, cited synthesis, one plan gate). — [Research a Decision (V6.12)](https://github.com/bmad-code-org/BMAD-METHOD/blob/V6.12/docs/plan/research-a-decision.md)
- Task Master: separate research model role (Perplexity, xAI, OpenRouter…), used via `--research` (documented for `analyze-complexity`). — [README](https://github.com/eyaltoledano/claude-task-master); [docs](https://docs.task-master.dev/capabilities/task-structure)
- Failure mode of research notes: in Böckeler's spec-kit trial, research notes describing *existing* classes were treated as new specs and duplicated. — [Böckeler 2025-10-15](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- Matt Pocock grilling: environment facts are found by sub-agents, never asked of the user (codebase, not web). — [grilling SKILL.md](https://github.com/mattpocock/skills/blob/main/skills/productivity/grilling/SKILL.md)

### Inferences
- A good design for /flow-plan research: research is triggered by explicit unknowns (spec-kit) and typed by decision (BMAD), produces one cited file, and must label "existing system facts" vs "new requirements" to avoid the duplication failure Böckeler saw.
- BMAD's Draft/Process modes are a cheap way to support users who already pay for deep-research tools, and suit a CLI that may run without web access.

### Gaps
- No quantitative evidence found that web research during planning improves outcomes.
- Exact Task Master `research` command doc returned 404 (2026-11-13).

## Q3. Critiques and field reports: what failed

### Takeaway
Critiques (2025-10 → 2026-10) are consistent: one heavy workflow for all sizes, markdown overload and double review, agents ignoring or over-obeying specs, specs that drift, and a "waterfall" feel. Tool makers responded in 2026 by right-sizing (Quick Spec, BMAD planning paths, spec-kit independent entry points). Thoughtworks keeps SDD/spec-kit at "Assess".

### Cited Findings
- Böckeler (Thoughtworks, 2025-10-15): Kiro turned a small bug fix into 4 user stories and 16 acceptance criteria; spec-kit "overkill" for a medium feature in an existing codebase; one spec = 8 files; "I'd rather review code than all these markdown files"; agents skipped steps or followed constitution "too zealously"; unclear functional vs technical split; asks where SDD sits on a problem size × clarity matrix; compares spec-as-source to MDD ("downsides of both MDD and LLMs"); "Verschlimmbesserung". Levels: spec-first, spec-anchored, spec-as-source. — [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- Zaninotto (Marmelab, 2025-11-12) "The Waterfall Strikes Back": a small spec-kit feature produced 8 files / ~1,300 lines; "80% of your time reading instead of thinking"; double review (technical spec contains code, then code again); an agent marked "verify implementation" done without writing unit tests; "mostly unusable" on large existing codebases; proposes plan mode + task lists, Lean-Startup loop (riskiest assumption → simplest experiment → build). — [Marmelab blog](https://marmelab.com/blog/2025/11/12/spec-driven-development-waterfall-strikes-back.html)
- Thoughtworks Radar: SDD technique at **Assess** (Nov 2025); GitHub Spec Kit at **Assess** (Apr 15, 2026): teams mostly in brownfield; constitution should cover scope, domain context, technology versions, coding standards, repo structure; problems = instruction bloat and context rot (one team moved reusable guidance into skills), unnecessary defensive checks, verbose markdown (fixed by limiting generated files); benefits most "experienced engineers with strong clean coding and architectural practices"; advises re-evaluating the need for SDD tooling as models improve. — [Radar: GitHub Spec Kit](https://www.thoughtworks.com/radar/languages-and-frameworks/github-spec-kit); [Radar: SDD](https://www.thoughtworks.com/radar/techniques/spec-driven-development); also OpenSpec at Assess (Apr 2026) as a "lightweight specification layer" — [Radar: OpenSpec](https://www.thoughtworks.com/radar/tools/openspec)
- Blog critiques (lower authority): spec drift ("the spec eventually still describes a system that no longer exists"; proof→spec feedback ignored) — [HackerNoon: the seams](https://hackernoon.com/spec-driven-development-has-a-blind-spot-the-seams); a case of 2,577 lines of Markdown for 689 lines of code (secondary report, original not verified) — [dev.to: SDD isn't waterfall but keeps ending up there](https://dev.to/pacheco/spec-driven-development-isnt-waterfall-but-it-keeps-ending-up-there-4eei); counter-argument "confuses writing a spec before coding with freezing a spec" — [kunalganglani.com](https://www.kunalganglani.com/blog/spec-driven-development-ai-agents)
- Academic (2026 preprints): "SDD as Prescribed and as Practiced" (Agarwal, Singhal, Macvean, Vasilescu, Breaux; v1 2026-08-25, v4 2026-10-15): 21 interviews (8 tool makers), 266 repos, 470,795 spec files from 73,030 repos; SDD used "selectively and mainly for new features"; specs often include implementation detail, which helps agents but makes specs prone to decay; spec-code checks happen mainly at completion; benefits may come from clarifying intent before delegating; more reliable agents but higher planning and review cost. — [arXiv 2608.25202](https://arxiv.org/abs/2608.25202). "EPIC Framework for SDD" (15 interviews): agents fill gaps with assumptions and declare incomplete work finished (from search snippet only). — [arXiv 2610.07534](https://arxiv.org/html/2610.07534v1)

### Inferences
- The dominant failure is cost/size mismatch, not the idea of specs. Coding Flow's story sizing (QUICK..STRICT) already addresses it on the run side; /flow-plan should right-size its output too (one story.md for small work).
- Separating "facts about the existing system" from "what to build" and keeping specs intent-level (not code) reduces drift and double review.

### Gaps
- No controlled study measuring defect or rework rates of SDD vs plan-mode vs no-plan found.

## Q4. Concrete techniques that improve plans, and evidence

### Takeaway
The best-specified techniques are spec-kit's (prioritized clarification with recommendations, "unit tests for English" checklists, read-only cross-artifact analysis with severities and coverage %) and Matt Pocock's design-tree grilling. Evidence is mostly practitioner/qualitative; the 2026 mining study supports "clarify intent before delegating" but gives no effect size.

### Cited Findings
- **Prioritized clarification** (spec-kit `/clarify`): scan spec against a taxonomy (functional scope, domain & data model incl. lifecycle/state transitions and scale, interaction/UX flow, NFRs: performance, scalability, reliability, observability, security, compliance; integrations incl. "protocol/versioning assumptions"; edge cases incl. rate limiting and concurrency conflicts; constraints & tradeoffs), mark Clear/Partial/Missing; max 5 questions per session, chosen by Impact × Uncertainty; EXACTLY ONE at a time; each with "Why it matters", a `**Recommended:**` option, 2-5 multiple-choice options or ≤5-word answer; answers written back into the spec; final coverage table (Resolved/Deferred/Clear/Outstanding). — [clarify.md](https://github.com/github/spec-kit/blob/main/templates/commands/clarify.md)
- **Rounds over a design tree** (Matt Pocock, 2026): ask all currently unblocked questions together, each with a recommendation; facts looked up by sub-agents. — [grilling](https://github.com/mattpocock/skills/blob/main/skills/productivity/grilling/SKILL.md). Contrast with superpowers: one open question, the one that "would change it most". — [brainstorming](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md)
- **"Unit tests for English"** (spec-kit `/checklist`): checklists test the *requirements*, not the implementation: items like "Is 'prominent display' quantified…?" tagged [Completeness]/[Clarity]/[Consistency]/[Measurability]/acceptance-criteria quality. — [checklist.md](https://github.com/github/spec-kit/blob/main/templates/commands/checklist.md)
- **Cross-artifact consistency analysis** (spec-kit `/analyze`): after tasks.md; "STRICTLY READ-ONLY"; detects duplication, ambiguity, underspecification, constitution conflicts (automatically CRITICAL), coverage gaps; severities CRITICAL/HIGH/MEDIUM/LOW; table with ID, location (file:line), recommendation; metrics: coverage % (requirements with ≥1 task), ambiguity and duplication counts; remediation only with user approval. — [analyze.md](https://github.com/github/spec-kit/blob/main/templates/commands/analyze.md)
- **Readiness gates**: spec-kit plan ERRORs on unresolved clarifications/gates — [plan.md](https://github.com/github/spec-kit/blob/main/templates/commands/plan.md); BMAD sprint-planning PASS/CONCERNS/FAIL and PRD *validate* mode — [BMAD planning path](https://github.com/bmad-code-org/BMAD-METHOD/blob/V6.12/docs/plan/choose-a-planning-path.md)
- **Assumption / decision logs**: ExecPlans Decision Log + Surprises & Discoveries — [OpenAI cookbook](https://developers.openai.com/cookbook/articles/codex_exec_plans); BMAD `.memlog.md` and `addendum.md` — [BMAD](https://github.com/bmad-code-org/BMAD-METHOD/blob/V6.12/docs/plan/choose-a-planning-path.md); ADRs + GLOSSARY.md via grill-with-docs — [mattpocock/skills](https://github.com/mattpocock/skills); `[NEEDS CLARIFICATION]` markers — [spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md)
- **Acceptance formats**: EARS in Kiro requirements (third-party) — [codemyspec](https://codemyspec.com/blog/kiro-specs-explained); Given/When/Then — [Böckeler](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html); behavior a human can verify with commands and expected output — [ExecPlans](https://developers.openai.com/cookbook/articles/codex_exec_plans); Kiro bugfix "unchanged behavior" section — [Kiro docs](https://kiro.dev/docs/specs/)
- **Intent definition** (BMAD): "what should be true when the work is done, what must not change, and what is out of scope". — [BMAD](https://github.com/bmad-code-org/BMAD-METHOD/blob/V6.12/docs/plan/choose-a-planning-path.md)
- **Kill option**: spec-kit assess ends in go / needs-clarification / kill; BMAD forge-idea lets ideas "die cheaply". — [spec-kit README](https://github.com/github/spec-kit); [BMAD](https://github.com/bmad-code-org/BMAD-METHOD/blob/V6.12/docs/plan/choose-a-planning-path.md)

## Q5 (scope addition). Web/JS-specific vs language/domain-agnostic

### Takeaway
Mechanisms in every tool are language-agnostic; the web bias sits in examples, in UX-centric artifacts and in the "schema → API → UI" vertical-slice template. Only BMAD ships a dedicated non-web domain module (games). Techniques that only make sense for web UIs: UX specs/front-end specs, loading/empty states, visual hierarchy checklists, "point at the UI" review.

### Cited Findings
- spec-kit: constitution defaults are CLI/library oriented (Library-First, CLI Interface with text I/O and JSON) — [spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md); README quick example is web (Vite + vanilla JS photo organizer with SQLite) — [README](https://github.com/github/spec-kit); clarify taxonomy is broad and backend-friendly (data volume, state transitions, throughput, observability, protocol/versioning, rate limiting, concurrency), with one UI category (error/empty/loading, accessibility) — [clarify.md](https://github.com/github/spec-kit/blob/main/templates/commands/clarify.md); checklist examples are UI-flavored ("visual hierarchy", "hover state", "prominent display") — [checklist.md](https://github.com/github/spec-kit/blob/main/templates/commands/checklist.md)

### Inferences
- For Coding Flow, "walking skeleton" and "vertical slice" must be redefined per project type: e.g. CLI = argv → core → stdout + exit code test; network service/protocol = handshake → one message type end-to-end over a real socket; game = one loop tick with input → state → render; embedded = boot → one sensor read → output on target/emulator; library = one public API call with doc test; data/ML = ingest → transform → evaluated metric. "UI" as a mandatory layer should be dropped from slice definitions.
- Domain-neutral clarification taxonomy should add categories spec-kit lacks: target platforms/toolchains, memory/latency/real-time budgets, wire formats and backward compatibility, determinism (games, ML reproducibility), hardware/OS constraints, packaging/distribution, API stability/semver for libraries. UX questions should be conditional on the project having a UI.

### Gaps
- No tool found publishing planning templates specifically for networking/protocols, embedded, or data/ML; only BMAD (games) offers a non-web domain module. Kiro and spec-kit language-agnosticism is inferred from neutral artifacts, not stated in docs fetched.
