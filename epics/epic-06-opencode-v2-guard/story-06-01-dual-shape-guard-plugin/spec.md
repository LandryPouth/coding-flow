# Story 06-01 — Dual-shape guard plugin (OpenCode 1.x and 2.x)

## User Value

A developer who upgrades OpenCode to 2.x keeps the guard. Today the upgrade
removes it without a word and the next `.env` write goes through.

## Requirements

- `PLUGIN_BODY` (`bin/lib/opencode.js`) keeps the V1 hook map and adds a V2
  entry: `export default { id: "coding-flow.guard", server: CodingFlowGuard,
  setup }`, where `setup(ctx)`:
  - returns immediately when `ctx`, `ctx.tool` or `ctx.tool.hook` is missing
    (OpenCode 1.19 calls `setup` with a partial context);
  - takes the directory from `ctx.location.directory`, falling back to
    `process.cwd()`;
  - registers `ctx.tool.hook("execute.before", (event) => …)` that runs the
    same check as the V1 hook on `{ tool: event.tool }` and `event.input`.
- The named export `CodingFlowGuard` is no longer exported (a module with both
  a named plugin export and a default V2 object is loaded twice by 1.x — keep
  one V1 entry: the default object's `server`). Verify on 1.19 that `server`
  is picked up; if not, keep the named export and document why.
- `toPayloads` accepts both argument vocabularies:
  - `write`: `a.filePath || a.path`, `a.content`;
  - `edit`: `a.filePath || a.path`, `a.newString`;
  - `bash` **or** `shell`: `a.command`;
  - `apply_patch` **or** `patch`: `a.patchText`.
- The MARKER line and version stay as they are, so `upgrade` regenerates
  existing plugins and `doctor`'s stale detection keeps working.

## Acceptance Criteria

- [ ] Given the generated plugin loaded by a V1-style harness (named/`server`
      hook called with `{ directory }`), when `write` targets `.env`, then the
      hook throws with the guard's reason.
- [ ] Given the generated plugin loaded by a V2-style harness (`default.setup`
      called with a fake `ctx.tool.hook` recorder), when the recorded hook is
      called with `{ tool: "write", input: { path: ".env", content: "A=1" } }`,
      then it throws.
- [ ] Given V2 `shell` with `echo A=1 > .env`, then it throws; given
      `edit` with `{ path: ".env", newString: "x" }`, then it throws; given
      `patch` with an `*** Add File: .env` section, then it throws.
- [ ] Given `setup` called with `{ options: {} }` (no `tool`), then it returns
      without throwing and registers nothing.
- [ ] Given a write to `src/a.js` with harmless content on either shape, then
      nothing throws.
- [ ] Manual, recorded in `tasks.md`: on a real OpenCode 2.x (isolated
      `HOME`/`XDG_CONFIG_HOME`), a model asked to write `.env` is refused by
      the write tool and by shell redirection; on OpenCode 1.19 the same.

## Edge Cases

- **Correctness**: an unknown V2 tool name maps to no payload (allow), same as
  V1 — epic-05 decides what "unchecked" means.
- **Compatibility**: plugins generated by 0.12.x stay recognised as ours
  (MARKER), so `upgrade` overwrites them without `--force`.
- **UX**: the thrown message is unchanged (`coding-flow guard: <reason>`), so
  the model-facing advice stays the same on both majors.
